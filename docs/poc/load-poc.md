# T1 부하 PoC 결과 — Lightsail 2GB 한 대가 버티는지

- 측정일: 2026-10-27 (codex 리뷰 세 차례 반영 후 다시 잼. 두 번째·세 번째 반영은 방송 간격과 S2 집계만 바꿔 S2만 다시 쟀고, S1·S3 값은 첫 번째 반영 뒤 측정이다. 세 번째 반영 때 방송 기록은 남아 있지 않아(발생기는 방송을 파일에 남기지 않음) 새 집계로 S2를 공식 실행으로 다시 돌렸다)
- 대상: 최소 게임 서버 `poc/load/server.ts`, 부하 발생기 `poc/load/run.ts` + `poc/load/lib/worker.ts`
- 결론: **Docker 내부 경로, 최소 서버 기준으로 S1~S3 모두 통과.**
  - 발생기는 서버와 같은 Docker 네트워크에서 붙었다. Caddy·TLS·인터넷 경로는 들어 있지 않다.
  - 서버는 찍기 막기·게으른 계산 공식 같은 실제 규칙이 빠진 최소 서버다.
  - "실패하면 바꿀 것"은 적용하지 않았고, 사용자 결정 요청은 없다.
  - SQLite 드라이버는 **better-sqlite3**로 정했다.
- 이 결과는 D25·D55·D56·D57의 사전 확인이다. 실제 서버 코드로 하는 최종 확인은 T14다.

### 계획과 다르게 한 것: 발생기를 Docker 네트워크 안에서 돌림

처음 계획은 발생기를 맥에서 돌려 `127.0.0.1:4100`(OrbStack 포트 포워더)으로 붙는 것이었다. 그렇게 재니 서버 밖에서 생긴 지연이 결과를 흔들었다.

- **지연이 크게 흔들렸다.** 같은 S1을 8번 돌리니 맥 경로의 응답 p99가 43ms~3,564ms였다. 같은 때 서버 안에서 잰 처리 시간(답을 받은 때부터 ack를 보낸 때까지)은 p99 60ms 이하였고, 이벤트 루프 지연 최대도 48ms 이하였다.
- **답이 사라지고 연결이 늦었다.** 한 번은 답 4건이 서버에 아예 닿지 않았다(서버 처리 수 996). 1,000연결을 맺는 데 13~17초가 걸린 적도 있다. 맥 `kern.ipc.somaxconn=128`과 포워더 쪽 재전송 때문으로 추정한다.
- **다시 켤 때 경로가 늦게 열렸다.** S3에서 컨테이너를 다시 켠 뒤 맥 경로가 열리기까지 4.3~4.8초가 걸렸다. 서버는 프로세스 시작 0.16초 뒤에 listen했다.

그래서 공식 측정은 같은 Docker 네트워크(`ktd-load-net`)의 발생기 컨테이너에서 `http://ktd-load:4100`으로 붙어 했다(`poc/load/gen.sh`). 서버의 CPU·메모리 제한과 통과 기준은 바꾸지 않았다. S3은 발생기 컨테이너에 docker 소켓을 붙여 Engine API로 `ktd-load`를 kill·start 한다. plan.md T1의 발생기 위치와 검증 명령도 이 방식으로 고쳤다.

- 파일 디스크립터 한계에 걸린 적은 없다. 발생기 컨테이너는 프로세스마다 20,480(프로세스마다 2,500연결)이고, 맥 셸은 `ulimit -n` 1,048,576이다. 10,000연결은 매번 모두 맺어졌다.

## 측정 방법 (판정에 쓰는 정의)

- **응답 시간**
  - 성공 ack만 모은 분포다. 시간 초과·거절·연결 끊김은 분포에 넣지 않고 오류율로 따로 센다.
  - 1ms 칸의 위쪽 경계로 기록한다. 칸 i는 (i−1, i]ms라서 500.4ms는 501로 잡혀 "≤ 500"을 통과하지 못한다. 방송 지연에도 같은 규칙을 쓴다.
- **지역 방송**
  - 서버는 같은 지역에 직전 방송을 실제로 보낸 뒤 1,000ms가 지나야 다음 방송을 보낸다. 예정 시각 `s` = 직전 실제 전송 시각 + 1,000ms(첫 방송은 그 순간)이고, 메시지에는 `s`와 실제 보낸 시각 `t`가 들어 있다. 서버는 25ms마다 지역을 돈다.
  - 고정 1초 격자를 쓰면서 최소 간격을 지키게 하면, 한 번 늦어진 만큼 계속 밀리다가 칸을 건너뛴다(30초 참고 실행에서 건너뛴 칸 6.7%). 그래서 예정 시각을 직전 전송에 맞췄다.
  - **방송 지연(예정 기준)**: 지역·방송마다 처음 도착한 시각 − `s`. 이벤트 루프 멈춤도 지연에 들어간다. 방송이 예정 `s`보다 늦게 `t`에 나가면, 그 사이 지나간 1초 주기(`s`+1초, `s`+2초, … ≤ `t`)를 그 방송을 받는 즉시 "건너뛴 방송"으로 센다. 건너뛴 방송의 지연은 도착 시각 − 그 주기 시각이다. 측정이 끝날 때는 마지막 방송 뒤 1초 주기 가운데 2초 넘게 지나도록 오지 않은 것도 건너뛴 방송으로 센다.
  - **도착 지연(연결마다)**: 각 연결의 도착 시각 − `s`
  - **전송 소요**: 도착 시각 − `t`
  - 시계 차이는 시작 때 `/health` 왕복으로 맞춘다.
  - **판정**:
    - 예정 기준 p95와 연결마다 p95가 모두 ≤ 2초
    - 1초에 1번 이하: 같은 예정 시각에 두 번 보낸 방송 0, **서로 다른 방송의 실제 전송 시각 간격 최소 ≥ 1,000ms**
    - 공백·누락: 아래 수치는 이번에 정한 값이다
      - 건너뛴 방송 비율 ≤ 0.1%
      - 실제 전송 간격(`t` − 직전 `t`) 최대 ≤ 3초
      - 방송을 하나도 못 받은 지역 0
      - 끝날 때 3초 넘게 조용한 지역 0
- **S2 발생량**
  - 발생기는 포아송으로 뽑은 예정 건수(planned)와 실제 보낸 건수(sent)를 센다. 준비된 연결이 없어 버린 건수(skippedNotReady)도 센다.
  - 판정은 세 가지다.
    - 예정 = 실제, 버림 0
    - 실제 발생률 ≥ 990/s (포아송 변동 허용)
    - 발생 구간 ≥ 600초
- **접속 수**
  - 서버가 측정 구간 동안 연결 수의 최솟값을 끊김 때마다 갱신한다. 판정은 이 최솟값 ≥ 10,000이다.
  - 1초 표본의 최솟값도 함께 남긴다.
- **메모리**
  - 서버 프로세스의 RSS 고수위 값(`/proc/self/status` VmHWM, `process.resourceUsage().maxRSS`)으로 판정한다. 측정 구간은 새 컨테이너에서 서버 프로세스가 시작한 때부터 S2가 끝날 때까지다(연결 맺기 포함).
  - cgroup `memory.peak`(페이지 캐시 포함)은 RSS와 따로 기록한다.
- **S3 ack 목록**
  - kill 뒤에는 새 답만 멈춘다. 진행 중인 답이 모두 성공·거절·오류(시간 초과·끊김)로 확정된 다음에 기록을 닫는다.
  - 그 기록의 성공 ack 전체를 DB와 대조한다.

## SQLite 드라이버 비교 (같은 시나리오, 같은 새 DB)

리뷰 반영 전 측정 코드로 쟀다. 응답 시간과 이벤트 루프 값은 측정 정의가 같다. 방송 지연은 옛 정의(실제 보낸 시각 기준)라 아래 본 결과와 직접 비교하지 않는다.

| 시나리오 | 지표 | better-sqlite3 | node:sqlite |
|---|---|---|---|
| S1 (3회) | 응답 p95 / p99 (ms) | 50·51·42 / 53·53·43 | 42·65·54 / 42·66·55 |
| S2 120초 | 응답 p95 / p99 (ms) | **94 / 125** | 149 / 204 |
| S2 120초 | 방송 전송 지연 p95 (ms) | **71** | 128 |
| S2 120초 | 이벤트 루프 p99 / 최대 (ms) | **86 / 197** | 147 / 287 |
| S2 120초 | RSS 최고 (MB, 1초 표본) | 305 | 300 |
| S2 120초 | 평균 CPU (코어) | 0.32 | 0.33 |
| S3 (맥 경로) | 누락 / 웨이브 이어짐 | 0 / 이어짐 | 0 / 이어짐 |

**고른 드라이버: better-sqlite3**

- 같은 부하에서 꼬리 지연(응답 p99, 이벤트 루프 p99)이 node:sqlite보다 40% 안팎 낮다. node:sqlite는 120초만 돌려도 이벤트 루프 기준(p99 ≤ 200ms)에 여유가 적었다.
- Node 22의 `node:sqlite`는 아직 실험 기능이다(시작할 때 ExperimentalWarning이 뜬다).
- better-sqlite3 13은 N-API로 미리 빌드한 파일(linux arm64·x64, darwin 등)을 패키지에 담고 있다. 그래서 컨테이너와 서버에서 컴파일 도구 없이 설치된다. 설치는 계획대로 서버(컨테이너) 안에서 한다.
- 메모리와 CPU는 두 드라이버가 거의 같다.

## 시나리오별 결과 (better-sqlite3, Docker 내부 경로)

### S1 한 지역 몰림 — 통과

R000 지킴이 1,000명이 연결한 뒤 **같은 순간에 1,000건을 한꺼번에** 보냈다. 1초 안에 흩지 않은, 가장 나쁜 몰림이다. 3회 결과다.

| 1,000건 정확히 한 번(중복 0, 누락 0) | 보냄 1,000 / ack 1,000 / 중복 ack 0 / 누락 0 / 서버 처리 수 +1,000 | ✅ |

### S3 강제 종료 — 통과

S2와 같은 부하를 40초 보내다가 `docker kill`로 껐다. 웨이브 경계를 하나 이상 넘기려고 **65초 기다린 뒤** 다시 켰다.

| 기준 | 결과 | 통과 |
|---|---|---|
| 응답 받은 정답이 DB에 모두 남음 | 확정된 성공 ack 40,050건 전부를 `recent_answers`와 대조: 누락 0. ack에 적힌 누적 포인트보다 DB 포인트가 작은 지킴이 0 | ✅ |
| 다시 켜고 5초 안에 응답 | start 요청부터 health 278ms, 첫 정답 ack 360ms (서버 프로세스는 시작 0.18초 뒤 응답) | ✅ |
| 웨이브가 저장 시각부터 이어짐 | 185개 지역 모두 웨이브 시작 시각이 같은 60초 격자 위(어긋남 0). 꺼진 동안 최소 1웨이브를 정산. 웨이브 1로 돌아간 지역 0. 현재 웨이브가 지금 시각을 따라잡음 | ✅ |

- kill 때 진행 중이던 답 90건은 끊김 오류로 확정됐다(ack 못 받음, 기준 밖). 확정 안 된 답 0건을 확인한 뒤 기록을 닫았다.
- 다시 켤 때 지역 화력을 `SUM(guardians.power)`로 다시 계산한다. 10초 화력 모음은 메모리에만 있다가 꺼지면 사라지기 때문이다. 다시 켠 뒤 185개 지역 모두 `next_power`가 지킴이 힘의 합과 같았다(불일치 0).
- 참고(맥 경로, 리뷰 전): 누락 0, 웨이브 이어짐은 같다. 첫 ack는 4.5~5.1초였는데, 포워더가 다시 열리는 데 걸린 시간이다.

## 바꾼 설정 (실패하면 바꿀 것)

- 적용한 것 없음. 모든 기준을 처음 설정으로 넘었다.
  - socket.io 기본값 그대로다. 서버는 polling·websocket 전송을 둘 다 받고, 발생기만 websocket을 쓴다. `perMessageDeflate`는 기본값으로 꺼져 있고, `maxHttpBufferSize`는 기본 1MB다.
  - 그 밖에 50ms 묶어 쓰기, `synchronous=FULL`, worker_threads 없음, JSON 파서
- 시험용 스위치는 남겨 두었다(T14 비교용)
  - `WS_ONLY=1`: websocket만 받기
  - `SMALL_BUFFER=1`: 버퍼 4KB, deflate 끔
  - `FLUSH_MS`, `SQLITE_SYNC`, `SQLITE_DRIVER`

## 남은 위험

- **이벤트 루프 p99 여유가 적다.** 10분 S2 네 번에서 176·170·116·106ms로, 기준 200ms에 가까운 실행이 있었다. 최대 멈춤은 0.4~1.4초였다. 실제 서버는 찍기 막기·게으른 계산·대표 뽑기 때문에 답 하나에 하는 일이 더 많다. T14에서 넘으면 "실패하면 바꿀 것" 2부터 적용한다(`synchronous=NORMAL`, 20ms, 바뀐 열만 쓰기 → worker_threads).
- **오래 돌 때를 모른다.** 10분만 쟀다. `recent_answers` 행 수, WAL 크기, RSS가 몇 시간 뒤에도 평평한지는 모른다.
- **실제 CPU는 다르다.** M4 Max 코어 하나로 묶었다. Lightsail 2GB는 버스트형 vCPU라 코어 하나가 이보다 느리고, 크레딧이 떨어지면 더 느려진다. 평균 0.34코어가 여유로 보여도, 같은 서버의 다른 앱과 버스트 크레딧을 나눠 쓴다.
- **네트워크 경로가 다르다.** 측정은 Docker 내부 경로에서 했다. 운영의 Caddy 프록시, TLS, 인터넷 지연, 학교망, Vercel 프록시 경로(long polling)는 재지 않았다.
- **최소 서버라 빠진 것이 있다.**
  - 찍기 막기, 하루 포인트 줄이기, 게으른 계산의 6웨이브 주기 공식(여기서는 한 웨이브씩 계산), BigInt, 대표 뽑기 10분 규칙, 지난 소식, 기록 지우기
  - 부하 시험 때만 서버가 정답 번호를 문제에 넣어 보낸다(`LOAD_TEST_REVEAL=1`, 발생기가 정답을 고르게 하려고). 실제 서버에서는 넣지 않는다.
- **끊긴 지킴이의 미처리 답**: 답을 큐에 넣은 뒤 ack 전에 소켓이 끊기고 바로 다시 붙으면, DB에 아직 안 쓴 값을 다시 읽을 수 있다. 실제 서버(T11~T12)에서는 지킴이 상태를 메모리에서 지우는 시점을 쓰기 완료 뒤로 미뤄야 한다.
- **실측 메모리**: 10,000연결에 RSS 고수위 307~316MB, cgroup 최고 340~363MB였다. systemd 추천값 `MemoryHigh=512M`, `MemoryMax=768M` 안에 들지만, 최종 값은 T14 실측으로 사용자에게 알린다.

## 다시 돌리는 법

```sh
uptime                                    # load 14 이하에서 시작, 다른 빌드·e2e 없이 혼자
pnpm -C poc/load install
pnpm -C poc/load seed                     # data/seed.db(지킴이 50,000명), data/guardians.json
docker build -t ktd-load poc/load
docker network create ktd-load-net
docker run -d --name ktd-load --network ktd-load-net --cpus=1 --memory=768m --memory-swap=768m \
  -p 127.0.0.1:4100:4100 -v ktd-load-db:/data -e SQLITE_DRIVER=better ktd-load
poc/load/gen.sh s1                        # 발생기 컨테이너(공식 측정)
poc/load/gen.sh s2                        # 600초. 짧게: poc/load/gen.sh s2 -e S2_SECONDS=60 (참고 실행으로 표시, 공식 통과 아님)
poc/load/gen.sh s3                        # docker 소켓으로 ktd-load를 kill·start 한다
poc/load/gen.sh s4
# 맥 경로(참고): pnpm -C poc/load s1 | s2 | s3 | s4
docker rm -f ktd-load && docker volume rm ktd-load-db && docker network rm ktd-load-net && docker rmi ktd-load
```

- 메모리 고수위 값은 다시 켜야 초기화된다. S2·S3은 `ktd-load` 컨테이너와 `ktd-load-db` 볼륨을 지우고 새로 만든 뒤 잰다. S1은 실행 전후 차이로 재므로 같은 DB에서 여러 번 돌려도 된다.
- 결과는 `poc/load/results/<시나리오>-<시각>/result.json`에 남는다(커밋하지 않음). 실행 중에는 같은 폴더에 보낸 답(S)·ack(A) 기록이 생기고, 이 기록으로 중복·누락을 센다.
